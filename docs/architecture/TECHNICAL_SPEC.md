## 📌 Executive Summary
**Pookie** is a real-time-like, turn-based mini-game platform crafted exclusively for couples. It eliminates heavy infrastructure costs (PostgreSQL, Redis, WebSocket clusters) by utilizing a highly optimized, serverless architecture running on **Google Apps Script** as a deterministic REST gateway and **Google Sheets** as an append/update transactional datastore.

The system features:
- **Low barrier to entry:** No accounts required. Instant 6-character room codes.
- **Four curated couple games:** Tic-Tac-Toe, Dots and Boxes, Couples Icebreaker Quiz, and SoulSync (Blind-Matching Bonding Quiz).
- **Optimistic Concurrency Control (OCC):** Prevents conflicting moves through incremental room versioning.
- **Adaptive Polling Heartbeat:** Minimizes Google Sheets API read quotas and preserves mobile battery life while maintaining responsive gameplay.
- **Automatic Lifecycle Cleanup:** Time-driven cron triggers automatically purge abandoned rooms without manual intervention.

## 1. Database Schema (Google Sheets Blueprint)

### 1.1 Sheet Structure Overview
The Google Spreadsheet contains two primary functional sheets:
1. `Rooms`: Active and recent game room sessions, player states, scores, and serialized board data.
2. `QuizQuestions`: A static catalog of icebreaker questions, categories, and options.
3. `RoomHistory` *(Optional Audit/Telemetry)*: Read-only archive of completed matches for game statistics.

### 1.4 Complex Game Board Serialization into Single Cells

In a spreadsheet datastore, storing game matrices across multiple rows or cells leads to high read/write lock contention. Instead, the game state is serialized into a single atomic JSON cell in Column `I` (`GameState`).

#### 1. Tic-Tac-Toe (3x3 Grid)
- **Cell Content (JSON string):**
```json
{
  "grid": ["X", null, "O", null, "X", null, null, null, "O"],
  "moveCount": 4,
  "winningLine": null,
  "winner": null
}
```
- **Serialization Rationale:**
  - `grid` is a 1D array of 9 elements (indexes `0` through `8`), mapped to the 3x3 board (`row = Math.floor(index / 3)`, `col = index % 3`).
  - Values: `"X"` (Host), `"O"` (Partner), or `null` (Unoccupied).
  - Compact footprint: < 80 characters.

---

#### 2. Dots and Boxes (Dynamic Multi-Variant Graph)
- **Grid Size Variants:**
  - **Small (3x3 Boxes / 4x4 Dots):** 9 boxes, 24 edges (12 H, 12 V). Fast casual gameplay (~2-3 mins).
  - **Medium (4x4 Boxes / 5x5 Dots):** 16 boxes, 40 edges (20 H, 20 V). Balanced strategic play (~5 mins).
  - **High (5x5 Boxes / 6x6 Dots):** 25 boxes, 60 edges (30 H, 30 V). Deep tactical territory warfare (~10 mins).
- **Cell Content (JSON string):**
```json
{
  "gridSize": 3,
  "claimedLines": {
    "H_0_0": "HOST",
    "V_0_1": "PARTNER",
    "H_1_0": "HOST"
  },
  "claimedBoxes": {
    "box_0_0": "HOST"
  },
  "hostBoxesCount": 1,
  "partnerBoxesCount": 0,
  "lastMoveAwardedExtraTurn": true,
  "winner": null
}
```
- **Serialization Rationale:**
  - Key-value mappings (`"H_r_c"` / `"V_r_c"` -> `playerId` or role) support arbitrary grid sizes (`gridSize` in `[3, 4, 5]`) with zero schema changes.
  - Box capture validation is calculated dynamically during `MAKE_MOVE`. If an edge completes 1 or 2 boxes, the box owner is stamped and `lastMoveAwardedExtraTurn` keeps `CurrentTurn` unchanged.
  - Total boxes needed to end the match: `gridSize * gridSize`.

#### 3. Couples Icebreaker Quiz
- **Cell Content (JSON string):**
```json
{
  "currentQuestionIndex": 2,
  "totalQuestions": 5,
  "questionId": "Q003",
  "category": "ROMANTIC",
  "questionText": "Who made the first romantic move?",
  "options": {
    "A": "Definitely me",
    "B": "Clearly them",
    "C": "It was completely mutual",
    "D": "Neither, destiny took over"
  },
  "hostAnswer": "A",
  "partnerAnswer": null,
  "answersRevealed": false,
  "roundMatches": 1,
  "completed": false
}
```
- **Serialization Rationale:**
  - Supports blind asynchronous inputs. While `partnerAnswer` is `null`, the client only sees `hasPartnerAnswered: false` without exposing the opponent's choice.
  - Once both answers are submitted, the backend sets `answersRevealed: true`, enabling simultaneous reveal animation.

#### 4. SoulSync (Blind-Matching Bonding Quiz)
- **Cell Content (JSON string):**
```json
{
  "currentRound": 1,
  "totalRounds": 5,
  "promptId": "SYNC_001",
  "promptText": "What was the exact moment you knew you had feelings for me?",
  "category": "INTIMACY",
  "phase": "JUDGING",
  "hostAnswer": "When we got soaked in the rain eating ice cream at 2 AM",
  "partnerAnswer": "The midnight walk in July when it poured rain",
  "answersRevealed": true,
  "verdicts": {
    "host": "MATCH",
    "partner": null
  },
  "playerReady": {
    "host": true,
    "partner": false
  },
  "coupleScore": 4,
  "completed": false
}
```
- **Serialization & Reducer Rationale:**
  - **Two-Phase Round Machine:**
    1. `phase = "ANSWERING"`: Both partners submit freeform secret strings. `GET_STATE` masks opponent's text until both submit.
    2. `phase = "JUDGING"`: Once both submit, `answersRevealed` flips to `true` and the UI reveals both strings side-by-side. Input fields are hidden.
  - **Manual Verdict Judging Engine:**
    - Replaces flaky automated fuzzy-string algorithms.
    - Each player selects either `"We Match (+2 Pts)"` or `"We Missed (-1 Pt)"`.
    - Player status switches to `"Ready"`.
    - When both submit via `SUBMIT_VERDICT`:
      - Both `MATCH` ➔ **+2 Pts**.
      - Either `MISS` ➔ **-1 Pt** (floor at 0).
    - Temporary text answers are purged and board state advances to the next prompt round.

## 3. Server-Side Lifecycles & Auto-Cleanup Logic

### 3.1 Background Cron Architecture
Google Apps Script provides native time-driven triggers. A scheduled trigger `cleanupInactiveRooms` executes every **10 minutes**.

```
[Time-Driven Trigger (every 10 min)]
               │
               ▼
   Acquire ScriptLock (Wait up to 10s)
               │
               ▼
   Fetch all rows in 'Rooms' Sheet
               │
               ▼
   Iterate through rooms & inspect:
     - (Now - LastActivity) > 30 mins
     - Status: ABANDONED vs FINISHED vs ACTIVE
               │
               ▼
   Partition rows: Keep vs Purge
               │
               ▼
   Batch overwrite / delete rows (Bottom-to-Top)
               │
               ▼
   Release ScriptLock & Log metrics
```

---

### 3.2 Cleanup Workflow Pseudocode
```javascript
/**
 * Cron trigger executed every 10 minutes.
 * Purges rooms that have been idle for > 30 minutes.
 */
function cleanupInactiveRooms() {
  const lock = LockService.getScriptLock();
  // Wait up to 10 seconds for concurrent write operations to yield
  if (!lock.tryLock(10000)) {
    Logger.log("Cleanup deferred: Could not acquire script lock.");
    return;
  }

  try {
    const ss = SpreadsheetApp.getActiveSpreadsheet();
    const sheet = ss.getSheetByName("Rooms");
    const lastRow = sheet.getLastRow();
    
    // Check if table contains data beyond headers
    if (lastRow <= 1) return;

    const dataRange = sheet.getRange(2, 1, lastRow - 1, 15);
    const rows = dataRange.getValues();
    const now = new Date().getTime();
    const INACTIVITY_THRESHOLD_MS = 30 * 60 * 1000; // 30 minutes
    const ABANDONED_GRACE_PERIOD_MS = 10 * 60 * 1000; // 10 minutes for mid-game disconnections

    const rowsToKeep = [];
    const roomsPurged = [];

    for (let i = 0; i < rows.length; i++) {
      const row = rows[i];
      const roomCode = row[0];
      const status = row[1];
      const lastActivityStr = row[13];
      const lastActivityTime = new Date(lastActivityStr).getTime();
      const idleDuration = now - lastActivityTime;

      let shouldDelete = false;

      if (isNaN(lastActivityTime) || idleDuration > INACTIVITY_THRESHOLD_MS) {
        // Exceeded 30 minutes of total silence
        shouldDelete = true;
      } else if (status === "ABANDONED" && idleDuration > ABANDONED_GRACE_PERIOD_MS) {
        // Abandoned room past grace period
        shouldDelete = true;
      }

      if (shouldDelete) {
        roomsPurged.push({ roomCode: roomCode, idleMinutes: Math.round(idleDuration / 60000) });
      } else {
        rowsToKeep.push(row);
      }
    }

    if (roomsPurged.length > 0) {
      // Clear existing data rows
      sheet.getRange(2, 1, lastRow - 1, 15).clearContent();

      // Write remaining active rooms back in a single atomic batch
      if (rowsToKeep.length > 0) {
        sheet.getRange(2, 1, rowsToKeep.length, 15).setValues(rowsToKeep);
      }
      
      Logger.log("Cleanup complete. Purged " + roomsPurged.length + " inactive rooms.");
    }
  } catch (error) {
    Logger.log("Error in cleanupInactiveRooms: " + error.toString());
  } finally {
    lock.releaseLock();
  }
}
```

### 3.3 Edge Cases Handling

1. **Mid-Game Connection Drop (One Player Leaves):**
   - If a player loses internet or kills the app, the heartbeat stops updating `LastActivity`.
   - The remaining partner will observe no move for 60 seconds and can tap *"Claim Abandonment"*, which transitions the room to `ABANDONED`.
   - If neither player interacts for 30 minutes, the room is permanently purged to prevent database bloat.

2. **Idle Finished Game vs. Active Game:**
   - A game marked `FINISHED` has already settled scores. If neither player initiates a rematch within 30 minutes, it is cleanly recycled.
   - Active games (`PLAYING`) are granted the same 30-minute ceiling: if no turn is submitted within 30 minutes, it is assumed the couple stopped playing, and the session expires.

3. **Atomic Deletion Safety:**
   - Rather than calling `sheet.deleteRow(rowIndex)` inside a loop (which shifts row indexes, causes off-by-one bugs, and incurs heavy GAS execution latency), the script extracts all rows in memory, filters out expired rows, and performs a single bulk write back to the sheet using `setValues()`.

## 4. Client-Side State Machine (Anti Gravity Integration)

### 4.1 Client Finite State Machine (FSM)

```
                ┌──────────────┐
                │    LOBBY     │
                └──────┬───────┘
                       │
         ┌─────────────┴─────────────┐
         ▼                           ▼
┌──────────────────┐       ┌──────────────────┐
│  CREATING_ROOM   │       │   JOINING_ROOM   │
└────────┬─────────┘       └─────────┬────────┘
         ▼                           │
┌──────────────────┐                 │
│WAITING_FOR_PARTNER│                │
└────────┬─────────┘                 │
         │ (Partner Joined)          │
         ▼                           ▼
┌─────────────────────────────────────────────┐
│               GAME_SELECTION                │
└──────────────────────┬──────────────────────┘
                       │
                       ▼
┌─────────────────────────────────────────────┐
│                GAME_PLAYING                 │
│  ┌───────────────┐       ┌───────────────┐  │
│  │    MY_TURN    │       │ OPPONENT_TURN │  │
│  └───────┬───────┘       └───────▲───────┘  │
│          │ (Submit Move)         │          │
│          ▼                       │          │
│  ┌───────────────┐               │          │
│  │EVALUATING_MOVE├───────────────┘          │
│  └───────────────┘                          │
└──────────────────────┬──────────────────────┘
                       │ (Win / Loss / Draw)
                       ▼
┌─────────────────────────────────────────────┐
│                  GAME_OVER                  │
└──────────────────────┬──────────────────────┘
                       │
                       ▼
┌─────────────────────────────────────────────┐
│              REMATCH_REQUESTED              │
└──────────────────────┬──────────────────────┘
                       │ (Both Accepted)
                       ▼
         [Return to GAME_PLAYING]
```

---

### 4.2 State Table & Transitions

| Current State | Trigger Event | Next State | Network Action / Polling Interval |
| :--- | :--- | :--- | :--- |
| `LOBBY` | Tap "Create Game" | `CREATING_ROOM` | POST `CREATE_ROOM` (No polling) |
| `LOBBY` | Tap "Join Game" | `JOINING_ROOM` | POST `JOIN_ROOM` (No polling) |
| `CREATING_ROOM` | Server responds with `roomCode` | `WAITING_FOR_PARTNER` | Start Polling at **4.0s** interval |
| `WAITING_FOR_PARTNER` | `partner` field is populated | `GAME_PLAYING` | Polling switches to **2.0s** (Host starts) |
| `JOINING_ROOM` | Server responds with RoomState | `GAME_PLAYING` | Polling switches to **2.0s** |
| `GAME_PLAYING (MY_TURN)` | User clicks a cell/edge | `EVALUATING_MOVE` | **Stop polling completely**; POST `MAKE_MOVE` |
| `EVALUATING_MOVE` | Move accepted & no game over | `GAME_PLAYING (OPPONENT_TURN)`| Resume Polling at **2.0s** |
| `GAME_PLAYING (OPPONENT_TURN)` | Polling detects turn switch | `GAME_PLAYING (MY_TURN)` | **Stop polling**; trigger haptic chime |
| `GAME_PLAYING` | Board terminal (Win/Draw) | `GAME_OVER` | Reduce polling to **3.0s** |
| `GAME_OVER` | Tap "Rematch" | `REMATCH_REQUESTED` | POST `RESET_GAME`; Poll at **2.5s** |
| `REMATCH_REQUESTED` | Both players ready | `GAME_PLAYING` | Resume game loop |

### 4.3 Heartbeat & Battery Optimization Architecture

Google Apps Script enforces standard quotas:
- Maximum URL fetch calls per day: 20,000 to 100,000 depending on workspace tier.
- Execution time limits: 6 minutes per script run.
- Polling blindly every 2 seconds will consume 1,800 requests/hour per player!

To ensure zero quota exhaustion and protect mobile battery, the Anti Gravity client implements a **4-Tier Adaptive Polling Strategy**:

```
           ┌─────────────────────────────────────────┐
           │        APP LIFECYCLE MONITOR            │
           └────────────────────┬────────────────────┘
                                │
               ┌────────────────┴────────────────┐
               ▼                                 ▼
      [App in Foreground]               [App Minimized / BG]
               │                                 │
     Is it Player's Turn?                        ▼
      ┌────────┴────────┐               PAUSE ALL POLLING
      ▼                 ▼               (Zero Quota Used)
   YES: MY_TURN    NO: OPPONENT_TURN
      │                 │
 POLLING PAUSED     ADAPTIVE 2s PULSE
 (Save CPU/Battery) ├── If idle > 45s: Backoff to 4s
                    └── Send Version 'v' Header (Return 304 if unchanged)
```

#### Optimization 1: Context-Driven Polling Elimination
- **During `MY_TURN`:** The opponent cannot make a move. Polling is **100% disabled**. The client waits entirely for local touch input.
- **During `OPPONENT_TURN`:** Polling runs at 2.0s with a ±200ms randomized jitter to prevent synchronous harmonic spikes against Google servers.

#### Optimization 2: ETag-Style Version Checking (`v` Parameter)
- When client polls `GET_STATE`, it attaches `&v=<current_local_version>`.
- The Google Apps Script checks Column `O` (`Version`). If `Version === v`, it returns a lightweight **58-byte payload**:
  `{"status":"SUCCESS","data":{"isUpdated":false,"version":2}}`
- Avoids serializing/transmitting board strings and eliminates mobile JSON parsing overhead.

#### Optimization 3: Exponential Idle Backoff
- If the opponent takes longer than 45 seconds to move:
  - 0s – 45s: 2.0s interval
  - 45s – 90s: 4.0s interval
  - > 90s: 6.0s interval
- The moment the opponent submits a move, the next poll immediately brings the game back to real-time.

#### Optimization 4: Mobile OS Lifecycle Hooks (Android / Browser)
- Utilizing `onPause()` / `onStop()` on Android, or `document.visibilityState === 'hidden'` in web views:
- When the screen turns off or the couple switches apps to check a message, the heartbeat loop is **paused immediately**. When the app returns to foreground, an instant single sync pulse is issued.

## 5. Security & Concurrency Considerations
1. **Optimistic Locking:** Every state mutation requires `expectedVersion`. If two requests overlap, the second request fails with `CONCURRENCY_CONFLICT`, preventing board overwrites.
2. **Server-Side Validation:** Move validity (e.g. cell not taken, turn order, line availability) is validated in the Apps Script before writing to the sheet.
3. **Player Authentication:** Lightweight UUIDv4 `HostId` / `PartnerId` tokens stored in client local storage prevent unauthorized third parties from spoofing turns.

## 6. Player Profiles, Dual PvP HUD & In-Game Social Dynamics

### 6.1 Gender-Based Profile Avatars
- Profiles capture player nickname and binary gender (`MALE` / `FEMALE`).
- Instead of generic placeholders, dedicated crisp SVG vector drawables (`ic_avatar_male.xml`, `ic_avatar_female.xml`) represent players on the profile setup screen, dual PvP HUD, and victory summaries.
- Player genders are exchanged during room creation and join operations, serialized in `gameState.playerGenders`, and mapped on clients.

### 6.2 Circular Turn Timer (`CircularTurnTimerView`) & Timeout Advantage
- To elevate turn clarity without occupying bulky screen real estate, a sleek circular countdown ring hugs the outer border of the active player's circular avatar:
  - **10-Second Countdown:** Continuously animates from 360° to 0° over the allotted turn window (10 seconds).
  - **Color State Transition:** Transitions smoothly from vibrant coral/primary pink (`#F06292`) during normal time to alert ruby crimson (`#E53935`) when remaining time falls below 25%.
  - **Timeout Advantage Resolution:** If the 10-second countdown runs out while the active player is still connected, turn advantage immediately passes to the partner (`move.isTimeout === true`) without forfeiting the game, ensuring uninterrupted casual flow.
  - **Disconnection Alert:** If polling heartbeats fail for 3 consecutive intervals (~6-9s) during active play, an alert dialog notifies the player that their partner lost connection, automatically resolving upon reconnection.

### 6.3 Dual PvP HUD & Below-Profile Reaction Display
- Avatars sit on opposing flanks of the arena header (Host vs Partner) with live match scores in between.
- When a player receives a reaction, a rounded badge pops in directly beneath that player's profile avatar, floats visibly for **5.0 seconds**, and smoothly fades out.

### 6.4 Arena Bottom Action Bar, Nudge Buzzer & Cooldown
- **Central Nudge Button:** An oversized, elevated circular action button (`bg_nudge_circle.xml`) sits prominently in the center of the bottom arena bar.
  - Tapping sends an instant `NUDGE` event with instant local tactile feedback.
  - Triggers a synchronized haptic vibration pattern on the receiving partner's device to playfully alert them when it's their turn.
- **5-Second Cooldown:** Tapping any reaction or nudge initiates a 5.0-second cooldown period during which all reaction buttons are grayed out (`alpha = 0.35f`) and disabled, preventing spam.
- **Flanking Reaction Bar:** Fast-reaction buttons flank the central nudge button:
  - `HEART` (Romantic appreciation)
  - `THUMBS_UP` (Encouragement / Good move)
  - `THUMBS_DOWN` (Playful teasing)
  - `LIGHTNING` (Competitive energy)
- **Zero-Emoji Architecture:** All reactions and buttons render pure vector SVGs to maintain clean, modern design standards without platform emoji inconsistencies.
